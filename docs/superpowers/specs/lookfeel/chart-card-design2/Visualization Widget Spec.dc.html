Visualization widgets · spec

Everything that is not the chart, or an input

Table, crosstab, freehand table, selection list and tree, current selection, range slider, KPI outputs and the title bar they share. The chart card spec treated the chart as one chart-owned object; this does the same for the other eight, and states what the modern gate already resolves for each versus what is still drawn from a hardcoded literal.

Decided in this document
§03The seed mark — a tri-state mark on the assembly, re-seeded onto a runtime clone, shipping as a condition of release. Card radius drops from 12px to 6px.
§04Compact is the default mode, and vertical padding defers to an author-set row height while horizontal padding does not.
§05The KPI hierarchy guidance drops, the title lane takes its own row at 20 / 26 / 30 so the anchored strip fits under compact, and the range slider is redrawn in CSS — its range band joining the derived selection fill, its handle gaining hover and press.

§09The shell owns any value it has a token for; the viz layer declares one only for a distinction the shell does not make. Three viz tokens retire; cell padding becomes a new shell step.

01

Three render paths, one appearance

The premise the shell and Composer specs are written on — a token changes a colour — does not hold here. A viewsheet widget's colour, type and row height reach the screen by three different routes, and only one of them is CSS. This is the fact that shapes every decision in this document.

A · Server format
VSFormat on the assembly

Cell background, foreground, border and font are resolved server-side into VSFormatModel and written to the DOM as inline styles — [style.color]="cell.vsFormatModel.foreground", 35 such bindings in the table components alone.

Appears in export. CSS cannot reach it without desyncing live view from PDF/Excel.
B · Server painter
Java2D / Batik draw

Slider, gauge, calendar and chart are drawn by painter classes on VSFloatable.getImage() — paintComponent(Graphics2D) onto a BufferedImage — with colour constants compiled in. No user format sits behind them.

Appears in export. Themed only by editing the constant.
C · Browser CSS
Component SCSS

Hover, focus, resize affordances, scrollbars, search boxes, drag lines, the mini toolbar. Everything transient and everything structural that never had a format behind it.

Live view only. The one path --inet-viz-* can drive.
The paths are not exclusive
Calendar and range slider sit on B and C at once: Angular components (vs-calendar.component.scss, vs-range-slider.component.scss) render them in the live viewer while the painters render them for export and print. Two renderers in two languages, one appearance to keep in agreement — which is why VSOutputChromeDefaults carries slider track, handle and tick colours in Java and the range slider still needs CSS work. Neither side alone covers the widget.
Unverified: which path the live viewer takes for gauges, thermometers and the painted slider. Confirm before relying on it.
The consequence

A visualization token that changes an export-visible surface has to be resolved on the server, as a format default, not in CSS. That is why the initiative grew a family of Java resolvers rather than a stylesheet. Path C alone would produce a product whose printout no longer matches its screen.

Every substitution lands on the DEFAULT tier of a clone, so USER and format.css tiers still win and nothing is persisted.

Calendar chrome is not dark-only
Decided

The dark branch exists because the shared MONTH_CALENDAR / YEAR_CALENDAR formats default to black text with no fill, which is dark-on-dark once the dashboard goes dark — a legibility bug. Light modern has no bug to fix, which is why it was skipped. But no bug is not the same as no work: with the gate on and dark off, every other widget picks up the modern neutrals and the calendar keeps legacy black-on-nothing, so it is the one assembly that visibly does not belong.

So it takes a light-modern branch on the same neutrals the title bar and table structure already use, and its gate moves from darkMode to modernObjectChrome. Dark stays a modifier layered on top, exactly as it is for the other five — which also removes the anomaly this section had to explain, that one sub-gate defaulted off and had to be opted into.

The substitution shape does not change: DEFAULT tier of a clone, USER and format.css tiers still winning, applied at both VSCalendarModel and the export painter. Only the palette and the gate change, so this is a branch inside an existing resolver rather than new machinery.

One resolver behaves differently

Five of the six compute their defaults at read, onto a clone the saved object never sees. VSObjectChromeDefaults instead seeds frame, radius and card background into the object at creation — correctly, because these are design-time defaults the author must be able to see and edit. The consequence is that seeding alone does not reverse when the gate turns off. Settled in §03 · the seed mark, which ships in the same branch: the full argument, the six gate states and what was rejected are all there.

Browser-side, _viz-tokens.scss declares 21 tokens under .viz-modern / [data-viz-theme="v2"]. Nine are consumed by a selector; twelve are vocabulary only. That ratio is the honest measure of how much of the widget set the CSS layer currently reaches.

03

The seed mark

Decided

One mechanism the rest of this document depends on twice — for card chrome here, and for density in §04. It is a decision taken against the branch, not something the branch does yet, and it ships as a condition of release.

Card radius is 6px
Decided

The seed writes CARD_CORNER_RADIUS = 12, justified in code as matching the annotation rectangle. It becomes 6px — --inet-radius-xl. That is the value Chart Card Spec v3 fixes for the same card, the value the shell ticket pulls the card tooltip onto so it matches, and the value the anchored toolbar pill already uses; 12px is off a scale that tops out at 6, and its cited precedent is author data set per annotation in the Format dialog rather than a card token.

The title lane settles it beyond the scale argument. Drawn at both values, a 12px radius consumes 12 of the lane’s 26px at each end, so the band’s fill pinches away from the corners and reads as a lozenge rather than the top of a card — worse under dense, where the lane is 20px and the curve takes more than half of it. The cost is legibility of the title bar, not taste.

Applies to all eight seeded assembly types, and because the seed already runs through setDefaultFormat it is a constant change, not new machinery. Nothing in the field carries either value, so there is no migration.

It does retire resolveSeededCorner() rather than re-point it. That check works today only because 12 has no legitimate collision — the same off-the-scale property that makes it wrong as a card radius is what makes it safe as a sentinel. 6px has the opposite character: it is --inet-radius-xl, and setDefaultFormat’s own format.css TableStyle lookup can write it into the DEFAULT tier, so a 6px test would strip a customer’s stylesheet radius — the overwrite-real-choices failure this section cites as the reason colour sniffing is unsafe, in radius form. No value test is needed: the mark records what was written, and re-seeding reproduces the correct value including that lookup.

Retiring it also removes a performance smell. getRoundCorner() reaches SreeEnv only by routing through resolveSeededCorner() to isModern() — two org-scoped property reads inside a format getter callers treat as free, in code that runs in loops. With the check gone the lookup leaves the getter, and resolving the gate once per render (§08 step 4) covers what is left.

Design discussion
Gate-off today is partial
Only the radius reverts. resolveSeededCorner() strips the seeded radius when the gate is off; the seeded border colour and card and page backgrounds have no equivalent and stay modern. An object created under the gate and read with it off would be square-cornered with warm-neutral chrome — a state neither mode was designed to produce. Because viz-updates has never shipped, no such object exists in the field: this is a hazard in the design, not damage to repair.
The asymmetry is defensible, not accidental: radius sniffing is safe because legacy is 0 and nothing else writes the seeded value, while #D9D5CC is a palette neutral a user could legitimately pick, so a colour strip would overwrite real choices. What is missing is not the strip — it is any statement that colours are deliberately one-way.
Design discussion
How seeding behaves today
The seed itself is correct at creation — setDefaultFormat reads the gate and writes modern or legacy accordingly, so a gate-off product seeds #DADADA and radius 0 as it always has. What is frozen is the decision. The mirror gap is the consequence that matters for rollout: an assembly created while the gate was off never receives modern chrome afterwards, so enabling the gate modernizes only what a customer builds next, not what they already have.
The two seeds also differ in reach. Border colour is written on every assembly type; the seeded radius is gated by isCornerSeedTarget(), an explicit positive list — table, crosstab, calc and embedded table, chart, selection list, selection tree, current selection. Range slider is deliberately excluded despite extending SelectionVSAssemblyInfo, and calendar carries its own radius. Those eight types are the population the 6px card radius in §03 applies to.
Design discussion
Why not simply move it to read time
It would gain clean reversibility and would modernize every existing dashboard with no migration. Those are real, and they are why the question keeps returning. Four things go wrong — the first is the one the seed mark is shaped to avoid.
1
Existing dashboards silently change shape. Every dashboard ever authored gains a 6px radius and a 1px frame on next open. Corner cells clip; assemblies butted edge to edge show page background through the rounded joins. Nobody opted in. A colour is forgivable that way — geometry is not.
2
The format editor goes blank. The author sees a framed, rounded card and an empty border field, because the value exists only on a runtime clone the editor never sees. Nothing to click, no indication where the frame came from.
3
Fixing that makes it permanent. To remove a radius with no visible source, the author sets radius 0 — which lands in the USER tier and outranks everything. That assembly now follows the gate in neither direction: the frozen state, manufactured at scale by frustrated users.
4
The complexity relocates rather than disappears. isCornerSeedTarget() is still needed or slider and calendar take radii they should not, and the format.css TableStyle radius lookup inside setDefaultFormat would have to run on every read or risk overriding a customer TableStyle.
Not a problem either way: exports. Both paths are server-side, so PDF, Excel and PNG stay consistent. The trade is that seeding buys author visibility and layout stability and pays in reversibility, while read time buys reversibility and pays in silently redrawn customer content.
The decision
The mark ships with the branch. viz-updates does not release until it is implemented, so gate reversibility is total from the first version any customer sees and no release ever exists that seeds unmarked assemblies. That is the whole reason to settle it now: the option is free before release and unrecoverable after.
Mark the assembly, and re-seed onto a runtime clone. A tri-state mark in VSAssemblyInfo's existing writeAttributes/parseAttributes records the gate value that was in force when setDefaultFormat ran — gate-on, gate-off, or before gate for anything created by a release that had neither. It is read by the chrome path and, per §04, by the density path too — so it records whether an assembly was created under the modern gate, not merely which chrome branch ran. It states what happened, not what the content is: because the master gate defaults off, gate-off is the mark most new assemblies carry, while before gate is the genuinely old content. The name holds only because the mark ships with the gate — if it ever lagged behind, unmarked would stop meaning pre-gate. On load, when the mark and the gate disagree, recompute the DEFAULT tier on a clone — the same shape as the other five read-time resolvers — instead of stripping values or rewriting saved content.
This is what makes it work where "just move it to read time" failed. Blanket read-time application redraws pre-mark dashboards with chrome they were never laid out for — failure 1 above; mark-keyed application leaves an unmarked assembly untouched, so pre-mark content is unaffected while marked content follows the gate in both directions. It also closes the mirror gap — a gate-off assembly is re-seeded forward when the gate turns on.
Mark the assembly, not the dashboard: seeding is per-assembly at creation, so a dashboard-level flag mislabels the mixed case — one dashboard can hold both assemblies that predate the mark and assemblies created after it, and a single flag has to lie about one of them. Re-seeding also reproduces the format.css TableStyle radius lookup already inside setDefaultFormat, which resolveSeededCorner() currently has to dodge by exception, and a designer's own colour is safe because it lives in the USER tier.
Design discussion
Why “before gate” still needs its own state
Every assembly in the field was created with the gate off, so treating before gate as gate-off would be factually accurate. Acting on it is the problem. With the gate on, mark ≠ gate then holds for every dashboard ever authored, all of them become eligible for forward re-seeding, and every one gains a frame and a 6px radius on next open: failure 1 of the read-time route above, arriving through the back door. So the third state is not about uncertainty, it is a policy switch — before gate means do not sweep, and pre-mark content stays as it is until someone decides otherwise. Keeping it separate from gate-off is what leaves that decision open rather than making it by default.

What this table does and does not cover
The table governs seeded values only — the frame, radius and card background VSObjectChromeDefaults writes into the saved asset at creation. Everything else in this document is read-time: a resolver substituting onto a clone, or a .viz-modern CSS rule. Read-time values are unmarked and always reversible, because nothing was written down — turn the gate off and they revert on every dashboard at once, before-gate and gate-on alike.
This is the distinction most easily misread across the two specs. The chart is one of the eight seeded types, so the chart card’s card chrome follows this table exactly; its tooltips, selection, type scale and toolbar are read-time CSS and the mark does not reach them. The visible consequence: a before-gate chart in a gate-on product is unmarked, so it keeps square corners and no frame while its tooltips and selection modernize anyway — modern overlays on a legacy card. That mixed object is what a designer actually sees, and it is the strongest argument for the Modernize bar below.
Opting a before-gate dashboard in
Before gate is not a permanent sentence, but nothing in the machinery lets a designer leave it — author edits land in the USER tier and never touch the mark. The opt-in needs no new migration path, because an old assembly genuinely was created with the gate off: modernizing it means asserting that fact. Stamp gate-off onto its unmarked assemblies and the existing re-seed runs — mark ≠ gate, DEFAULT tier recomputed forward onto a clone, assembly renders modern. Read the third state as unclaimed rather than old, and migration is the moment someone claims it.
Stamp the whole dashboard, not one assembly: a half-migrated dashboard is the mixed-appearance problem again. It is an ordinary document edit, so it saves with the dashboard, follows normal undo, and un-stamping returns the assembly to unclaimed. Afterwards that dashboard follows the gate in both directions like any other — turn the gate off and it returns to legacy chrome. It is no longer frozen.
What it must not be is implicit on save. Stamping silently when a designer opens and saves an old dashboard would change its appearance as a side effect of unrelated work — the retroactive-geometry failure with an extra step.
Proposed — a dismissible bar above the canvas
A once-per-dashboard action should not hold permanent toolbar space. A bar carries the right meaning on its own: it is temporary, it is about this dashboard, and it leaves when the question is answered. It appears only while the open dashboard holds unmarked assemblies and the gate is on.

What it costs
The mark is a day: a nullable field on VSAssemblyInfo, one line each in writeAttributes and parseAttributes, clone/copyViewInfo handling, and two lines in setDefaultFormat to record which branch ran. The re-seed is one resolver-shaped code path in the two places the other resolvers already run — runtime model build and the export painters — plus coverage for all six mark-and-gate states, two of which re-seed. No migration at all, since nothing in the field predates it, and no write against customer assets. Because it adds read-time work by design, resolve the gate once per render as part of the same change rather than as a follow-up.
Design discussion
Considered and not taken — persisting the re-seed
Rewriting the saved object instead of a clone would make the corrected values visible in the format editor, but it buys a versioning story on import and a write against saved customer content whose blast radius is every marked assembly at once. It acquires a migration obligation too, though only for content created after the branch ships — not, as things stand, for anything that exists now. This is the one place the clone route gives something up: §02 justifies seeding on format-editor visibility, and a corrected-on-clone assembly shows the stale seeded value in the dialog while rendering the corrected one. Narrow — it only occurs when the gate has changed since creation — but if that divergence is the complaint, persisting is the answer.
Design discussion
What was weighed
Against
Nothing is broken in the field yet. The branch has not shipped, so the partial reversal has harmed no customer and no schedule is held by it — design debt paid before it is owed, which can legitimately sequence behind work that has users waiting.
Against
It is a persisted attribute, serialized into saved assets and read on import — schema versioning, in a rollout whose first steps are deliberately export-safe. Shipping it pre-release is what keeps that a one-time cost instead of a versioned migration.
Decisive
The cohort needing migration is currently empty, and only stays that way until the branch ships. Every assembly created after the gate reaches a customer without a mark is one that can never be reasoned about later without value-sniffing. There is no cheaper moment than before release, and no way back to one.
Decisive
Every future seeded default would inherit the flaw, arriving one-way and unmarked. The mark makes seeding a reversible mechanism rather than a one-way write, so the next design-time default costs nothing extra.
04

Density is a persisted number, not a token

Before the initiative, one constant — AssetUtil.defh = 20 — was the default data row height, header row height, title height, selection-list cell height and list-input cell height, for every assembly. It is a persisted model value: an author who has ever dragged a row edge owns that number forever, and no stylesheet can move it.

That is why VSDensityDefaults resolves height server-side and applies it only where the assembly still carries the legacy default. Dense is pinned to 20px rather than to the design spec's 26px for the same reason: it has to equal today.

Compact is the default, and the mark is what makes that safe
The specified default is compact, not dense: 24px rows, the density the design intends. Dense is not legacy-exact, and it is worth being precise about that, because “dense equals today” is the claim both the seed mark and this default lean on. Of the six roles in the matrix below it preserves two — data row and selection cell, both 20px — and diverges in four: header row 20 → 22px, cell padding 8/6 → 4/3, the declared toolbar height 30 → 24, and font size 13 → 12px. All four are branch values, not decisions taken here. What dense does guarantee is the server row height an assembly is laid out against, which is why nothing reflows; the title lane joins that guarantee at 20px per §05, and list-input height comes from defh rather than from this matrix.
On its own that would reflow the estate. VSDensityDefaults is a read-time resolver with no per-assembly condition, so raising the default would grow every saved table 20 → 24 the moment the gate turned on — the retroactive-geometry failure, in the one dimension that pushes content down the page. Two floors the matrix does not scale

The CSS fallback mode is dense, not compact
_viz-tokens.scss scopes the matrices as .viz-modern.viz-density-, and bare .viz-modern shares its block with .viz-density-dense — so an element with the modern class but no density class resolves to dense. That was harmless while dense was the default. The density body class must be emitted unconditionally whenever viz-modern is, or the bare .viz-modern block has to carry compact’s values instead of dense’s. Pick one and state it in the ticket — this is exactly the class of defect that ships silently.

The two density layers can disagree
Decided

Server height applies only to assemblies still on the legacy default; the DOM padding tokens apply unconditionally to any surface that consumes them. A table whose author set a 32px row height gets comfortable padding inside a dense row, or the reverse. The asymmetry is the defect — the server layer already stands down when an author owns the height, and the DOM layer stands down for nothing, because a token cannot see that a row was resized.

Vertical padding defers to an author-set height; horizontal padding does not. Where the author owns the row height, that assembly leaves the density system vertically and takes legacy padding-y 6px, so the proportions they set are the ones they keep. Column padding never interacts with row height, so compact’s 6px padding-x applies to a resized table exactly as it does anywhere else. Deferring both would opt a table out of half the density system for no reason.

This is not free in CSS: the density scope has to be emitted per assembly rather than once per page, so the server can decline to emit it for assemblies that are not on the legacy default. That is the same shift to per-assembly resolution the seed mark already requires, so it ships in that change rather than after it.

One check belongs in the ticket: an author-set height that happens to equal defh 20 must be distinguishable from one never set. If it is not, deferral misfires on tables an author deliberately pinned to 20 — the value-sniffing trap of resolveSeededCorner() again, and the mark is the same answer.

The KPI hierarchy has nothing to attach to
Decided

The design spec asks for comparison and sparkline to read as subordinate to the primary value. That is a hierarchy statement, and hierarchy needs a container to live in. There is no KPI composite — text, gauge and image are independent assemblies an author drags into place — so nothing in the product knows which value is primary.

The guidance drops. KPI is an authoring pattern, not a component. A rule no resolver can enforce is worse than no rule: it invites implementation against a promise the code will not keep, and it leaves this document carrying a permanent gap that is really a scope error. The subordination language comes out of the design spec, and this section stops claiming a KPI widget exists.

A real KPI composite stays open as a product decision — value, comparison and sparkline as slots, with the hierarchy structural and therefore stylable. It is a new assembly type with its own editor, binding and export path, which is a different initiative from chrome defaults.

The anchored strip does not fit the title lane
Decided

First, the collision as previously written was wrong. min-width: --inet-control-height-md is on the button and is horizontal — a 30px width floor for an icon target, making no claim on height. The strip’s height is a hardcoded height: 24px on .mini-toolbar-container under :host-context(.viz-modern), coupled to GuiTool.MINI_TOOLBAR_HEIGHT_MODERN. So the real figure is 24 into 20, not 30 into 20 — and under a coarse pointer the strip already overrides to min-height: --inet-control-height-touch with overflow: visible, overflowing the lane by 24px on purpose.

The lane grows; the strip keeps its size. Title height joins the density matrix as its own row at 20 / 26 / 30 — dense pinned to defh, compact and comfortable borrowing the header row’s steps. Compact’s 26px lane holds the 24px strip with 1px clearance either side, so it fits by construction. Dense stays 20px, which is the point: it is the one mode that must equal today, and the anchored strip is unavailable there anyway.

A 24px strip cannot fit a 20px lane, so the anchored strip is a compact-and-above affordance. Dense falls back to the existing hover-revealed overlay — the legacy .mini-toolbar:hover path, already shipping, no new code. That is the right split on its own terms: dense exists to maximise data, and a strip visible at rest is a comfort affordance. Touch is unaffected either way, since its 44px floor overflows any lane height by design.

Two consequences. Because heights move only for marked gate-on assemblies (§03, §04), a before-gate dashboard keeps its 20px lane and never hosts an anchored strip — the strip is isVizModern()-gated regardless. And the hardcoded 24px should become --inet-control-height-sm, which is that same 24px as a shipped step; that also settles the control-height conflict in §09, where the chart card spec already names -sm for the overlaid strip.

The selection-state bridge

Decided

Why the widget set still looks unfinished under the gate, and the last of the five decisions this document settles. --inet-viz-selected-bg and --inet-viz-selected-text are exposed and modern-valued, but their only consumer is the combo-box dropdown. What a customer sees today

The table cell they were actually looking at does not.
What the bridge costs now
No sixth resolver. The two properties join the per-assembly DEFAULT-tier recompute the seed mark already builds (§03), so the work is two more values in an existing path rather than a new class with its own sub-gate. It still changes export output, so it still needs the manual pass the chart selection change needed — and it ships with the chart’s selection vocabulary, not separately, or the product carries two selection idioms in one dashboard.
Derive it, and ride the re-seed path
Decided

Both tokens are withdrawn, and selection is derived instead. Data selection is --inet-primary-color at 28% over the cell, with text left at its normal foreground — the same construction the chart card already ships. That retires --inet-viz-selected-bg and --inet-viz-selected-text rather than wiring them up: a derived value cannot drift from the shell’s focus family, and the theme editor still controls selection, through primary, with no dedicated control to keep honest. The viz layer’s teal #DDF1F5 family retires with them, which settles the first row of §09 by construction rather than by agreement.

No sixth resolver. The two derived values are two more properties in the per-assembly DEFAULT-tier recompute §03 already introduces. A standalone class was the right shape before the mark existed; it is now a second mechanism for the same job.

The tint is flattened against the assembly background, not composited per cell. This is the part that would otherwise be decided by whoever hits it: 28% alpha is free in CSS but VSFormat backgrounds are solid, so the server has to resolve the tint to one colour — and what sits underneath varies with banded rows and conditional fills. Flatten once against the assembly background. On a banded row the result is a few percent off a true composite, which is invisible next to the cost of per-cell compositing in the painters, and it keeps one selection colour per assembly instead of a family that shifts row to row.

The calendar takes the same fill, with a border on range endpoints only, because an interval selection cannot show where it starts and stops from fill alone — reasoned below. One consequence to accept: a conditional fill dark enough to swallow a 28% tint will show selection weakly. That is already true of the chart’s treatment and is the correct trade — a selection highlight should not outrank data the author deliberately coloured.

Design discussion
Why the calendar needs a border as well

Two of the three objections to putting the calendar on this fill do not survive inspection. Cell size favours it: a 2px border on a small day cell crowds the numeral where a tint does not. Compositing resolves cleanly too, because .day-cell carries no background of its own — with the caveat that the --surface classes put month and day-title cells on --inet-shell-surface-subtle, so one flattened tint lands a few percent off there. That is the same trade accepted above for banded rows.

The third is real. A fill loses range endpoints. Calendar selection is frequently an interval, and a flat 28% tint across contiguous cells reads as one continuous band with no indication of where it starts and stops. A table does not have this problem — a table selection is a set of rows, not a range. So the fill is right for the interior and insufficient on its own: all four borders on the endpoint cells, none in the interior, both values derived from primary. That keeps this vocabulary intact rather than forking it, and it mirrors how the chart card separates selected from focused.

The ownership rule
Decided

The four remaining conflicts were one mistake in four sets of clothes: a value chosen well inside one layer, with no rule saying which layer owns it. Because both layers answer to the same gate, there is no boundary to negotiate at.

A value belongs to the shell whenever the shell has a shipped token for it. The visualization layer may declare a value only where it needs a distinction the shell does not make — density being the whole of that case. Distinct because visualization is different is a reason; distinct because visualization is separate is not, and on one gate it is not even true.

Read against that rule the four resolve without further argument. --inet-viz-toolbar-height’s 28px compact step is redundant — the shell scale goes 24/30/36/44 and §05 already put the anchored strip on --inet-control-height-sm — so the token keeps only the steps the shell lacks, which is none, and retires. --inet-viz-font-size at 12px restates --inet-font-size-base, which the shell ticket had just finished removing from the tooltips; it retires too. Hover fill’s cool #EEF4F6 restates the warm --inet-hover-secondary-bg-color with no distinction to point at. The audit’s "fifth structural neutral" turned out to be a fourth instance of the same thing, not a gap: #C8C2B7 is already $shell-border-strong in _variables.scss, and --inet-viz-pinned-divider merely restates its hex. And the binding already exists: $shell-border-strong flows to --inet-shell-border-strong to --inet-border-strong-color, which _viz-tokens.scss line 43 correctly assigns to the divider. The defect is that line 98 re-declares the same token as the literal inside a mode block, overriding the base block’s derivation — so the work is deleting one line, not adding a token. The gap was an artefact of auditing custom properties without the SCSS beneath them, and of reading a mode-block override as the definition. Cell padding is the one survivor with a real claim: 3px is below the space scale, but a data grid genuinely needs a tighter step than any shell surface — so the answer is a new shell step, not a viz-local literal.

Two earlier closures show why the rule is worded around tokens rather than authority. Selection colour was the fifth conflict and §07 closed it by derivation — deriving from --inet-primary-color retires both viz tokens, so the layers cannot restate each other at all. Card radius was the clearest instance and §03 settled it at 6px the same way. Where a value can be derived or borrowed, prefer that to adjudicating it: a precedence rule settles an argument, a shared token removes the ability to have one.

The four gaps are not covered by this rule and stay open on their own terms; none is a disagreement, each is an absence, and they are tracked as rows in the table above.
