Chart alignment · spec

The chart card, as chart-owned geometry

The chart emits title band, legend, border and plot as one object, so the card is chart-owned geometry rather than host chrome — this spec covers all of it. Sizing is expressed as rules first — which boxes flex and which size to their content — because authors resize charts and toggle elements per chart. §04 states the default-density values those rules resolve to.

01

Anatomy

Four lanes, top to bottom. Chrome is intrinsic — each region sizes to its own content, and the plot is the remainder. No region of the card is sized from an absolute coordinate; every band is a content box, which is what keeps the model resolution-independent. The toolbar strip is the one exception, and it is not a region: it is absolutely positioned over the title lane rather than sized into it (§04, §10.1).

Card radius — the seed moves to 6px, and three things move with it
decided
The edit itself is CARD_CORNER_RADIUS = 12 → 6 in VSObjectChromeDefaults.java. It is one line, and it is not self-contained.
Check the annotation rectangle first. The constant's comment says 12px matches the annotation-rectangle radius. If that is still true, dropping to 6px either breaks that alignment or takes the annotation with it. Confirm which before landing — this spec has not read the annotation value, and the comment is the only evidence for it.
The gate-strip is an equality test, so changing the seed changes what it catches. resolveSeededCorner reverts a DEFAULT-tier radius to square only when it is exactly equal to the seed. Any asset already carrying a 12px seed stops matching the moment the constant becomes 6, and would keep its rounded corners with the gate off — the partial-reversal state the whole mechanism exists to avoid.
So confirm the 12px cohort is empty before landing — do not assume it. Two gates share a name and must not be conflated here. Seeding is decided server-side: VSObjectChromeDefaults.isModern() reads viewsheet.modernVisualization and viewsheet.modernObjectChrome straight from SreeEnv, and the seed is written at creation through setDefaultFormat. The .viz-modern body class gates browser CSS only and has no part in seeding, so the fact that nothing in the client sets it proves nothing about what has been seeded. Both properties default off, and an EM control exists for them — so the question is whether any deployment has enabled viewsheet.modernVisualization, which this spec has not established. If no org has, the change is one line. If any org has, it needs a migration rewriting DEFAULT-tier 12px radii to 6px, or those assets keep rounded corners with the gate off. Either way the window closes once the gate ships broadly — the same window the seed mark is racing.
Sequencing follows from the third point rather than from preference: land this before the gate is enabled anywhere, and it stays a one-line change. It also removes the only value in this spec that had no home on the shipped radius scale, so §07's token map needs no new declaration.
02

Toolbar — from floating overlay to anchored strip

Two changes, and the second is the one that matters to users. Today mini-toolbar.component is an overlay: absolutely positioned at z-index 9920, hidden until hover, floating above the assembly at topY = top − 28 − adj. It moves into the title lane instead — and the kebab stops hiding wherever hover cannot reveal it, so on touch the card announces that it has controls before anyone touches it, while a mouse or trackpad still reveals the strip on hover (§10.1). Every visibility predicate is reused verbatim and no gating logic changes — what the strip shows in any given state is still decided by exactly the code that decides it today. The action set does change, in the six scoped edits listed below.

The resting kebab is a touch and keyboard affordance, not a mouse-discoverability fix. On a pointer device the strip is largely self-revealing — a viewer scanning a dashboard sweeps the pointer across cards and it appears — so little is claimed there. What has no hover to sweep is touch, where the action buttons do not render at all today, and the keyboard, where a control that exists only on hover has no resting focus target. Those two cases are the justification, and the strip gets a resting state for them. So the resting draw is scoped to the devices that need it, by capability rather than by device. On mouse or trackpad the lane is empty until hover or focus, and then the kebab and the three stable actions fade in together. The lane reserves the full strip width in every state, so nothing moves when they appear. The mechanism is §10.1 — the capability query, the requirement to hide with opacity rather than display: none, and the hybrid-laptop case. Beyond the pointer rule the resting draw has exactly two exceptions, both deliberate: a live Hide MiniToolbar dismissal (below), and a card too short to host any control at all — §06 removes the kebab below 32px, where right-click becomes the only route.

How the strip stays legible — §10
The card background is author-set, so the strip cannot carry a fixed treatment. Two rules govern it, and both are general enough that the toolbar is only their first consumer, so they are specified in §10 rather than here: §10.1 the capability query that decides whether the strip is drawn at rest, and §10.2 the two glyph tones derived from the background's luminance, replacing the white bordered box. §10.2 also carries the one implementation precondition — the glyph is an <img> today, which color cannot tint.
Turning the toolbar off stays exactly as it is — and it outranks the resting kebab
do not change
Two independent suppression mechanisms exist today. This spec changes neither, and both win over everything in §02. A deployment that turns the toolbar off sees no strip, no kebab and no resting glyph — anchoring and the resting state describe what the strip looks like when it is shown at all.
Per-action visibility. Every predicate in the document is guarded by isActionVisible(name), which tests the server-supplied model.actionNames deny-list — the hook through which actions are turned on and off outside the client. Hiding every toolbar action this way empties the strip. The cap of three is applied to whatever survives these predicates, never to the declared set, so suppression composes with it correctly and needs no special case.
Per-assembly dismissal at runtime — and it is transient. createToolbarActions prepends a close-icon "Hide MiniToolbar" action calling miniToolbarService.hideMiniToolbar(absoluteName). The service holds one hideMiniToolbarAssembly string, not a set, and handleMouseEnter clears it once the pointer leaves and returns. So this is a get-out-of-my-way for the current hover, not a stored preference — dismiss it, move away, come back, and the strip is there again. It is gated by isActionVisible("Hide MiniToolbar"), so a deployment can remove it entirely.
The resting kebab must honour the dismissal while it lasts. A persistent glyph that survived "Hide MiniToolbar" would make the action useless, so dismissing hides the whole strip including the kebab, with right-click as the route back. But note what the transience means: this is not the opt-out for anyone who dislikes permanent chrome — it returns on the next hover. If the resting kebab draws that complaint, the answer is the per-action deny-list above, or a new preference; not this control.
Why keep it at all, once the strip cannot cover a neighbour? The dismissal almost certainly exists because a floating toolbar overlaps whatever sits above the assembly, and anchoring removes that reason entirely. But §02 replaces it with a narrower one. §10.1 removes most of the ink this control was being kept for: on a pointer device the lane is empty at rest, so there is no permanent glyph to want gone. What remains is touch, where the kebab is drawn at rest on every assembly — and touch is also where the dismissal is least useful, since it is cleared by a hover that never comes. So the argument for keeping it is no longer "chrome becomes permanent"; it is that withdrawing an existing escape hatch in the same release that changes resting behaviour spends goodwill for nothing. It also still earns its place in the title-hidden state, where the strip does overlay the plot's top-right corner.
One consequence for the cap, listed as the sixth source edit above: the close action is spliced in at index 0, ahead of everything §02 reorders, so a naive "first three visible" spends a slot on it. It belongs in the menu, alongside the other things done to the strip rather than to the chart. Worth confirming against a running build how it renders in the floating strip today, since it is the one toolbar entry that is not an assembly action.

Generalizing beyond charts — the card is the pilot
separate document
Seven other assemblies float a toolbar today. hasMiniToolbar() lists table, crosstab, calc table, calendar, selection list, selection tree and selection container, plus the range slider when it is an adhoc filter — and no small input widget at all: spinner, slider, combo box, checkbox and the rest never receive one, before or after this change. Every type on that list except the range slider already declares titleVisible, so anchoring needs no new structure anywhere.
The one decision with app-wide consequences is settled: a title-hidden assembly reserves nothing. Had it reserved a condensed lane, every title-hidden table and selection list in every existing dashboard would gain ~30px of chrome and lose that much content — a pixel-positioned break across a customer's whole portfolio. Overlaying the strip inside the card's top-right costs no layout and still buys everything anchoring is for: it moves with the assembly, stays inside the border, and is no longer clamped against viewport bounds. §03 specifies it for the chart, and that is the answer for all eight.
The rest is recorded in Anchoring beyond charts - discussion.md, and the rollout is now three slices in: chart, then table/crosstab/calc table, then selection list and tree, which are anchored but not capped — AbstractVSActions.kebabOnly makes the kebab their whole strip at any width, so the cap of three is a chart-and-table rule rather than a ceiling the narrow family shares. Also recorded there: that selection containers already suppress child toolbars and the anchored design must inherit that rather than rediscover it; and that VSRangeSliderModel has no titleVisible at all — its title takes a titleRatio of the width beside the slider, so it has no lane to anchor into and should stay outside the pattern.
Deliberately not in scope: which actions deserve to be toolbar actions, how selection gating should work, and whether the menu's grouping is right. Those are all live questions, but they are separable from moving the strip — and answering them here is what turned earlier drafts of this section into a re-specification of the action model.
03

Title hidden — overlay, never reserve

The lane belongs to the title. Hide the title and the lane goes with it: the plot starts at the card's 12px inset, and the strip overlays the plot's top-right corner on its own small surface. Nothing is reserved, so hiding a title returns every pixel to the plot — and rolling this pattern out to the other seven assembly types cannot reflow a single existing dashboard. The topmost tick label still gets its clearance, but that is the plot's own internal padding, which it already has today.

Why overlay rather than a condensed lane
decided
The alternative was a collapsed lane of roughly 28–32px whenever the title is hidden. It reads more tidily in isolation and it is the wrong choice, for one reason that only appears at scale.
Dashboards are pixel-positioned. A reserved lane means every title-hidden assembly in every saved dashboard gains ~30px of chrome and loses that much content — across a customer's whole portfolio, on upgrade, with no author action. Overlaying costs nothing and breaks nothing. The lane is free where a title already exists; where it does not, it is not worth a migration.
Everything anchoring is for still holds. The strip moves with the assembly, stays inside its border, cannot cover a neighbour, and needs no viewport clamping — none of that depended on reserving space.
The cost is honest: in this state the strip does cover a corner of the plot. It sits on --inet-card-bg-color at 94% with --inet-shadow-low and --inet-radius-md, so it reads as a layer above the plot rather than a hole in it — and it is the top-right corner, which is empty on most chart types.
Resting state still applies, on the same terms as §02. Touch draws the kebab here too, over the plot corner; pointer devices reveal it on hover. A single dim glyph is the price of the object being discoverable at all when it has no title — and this is the state that needs the scrim, since the glyph sits on plotted data rather than on a band whose luminance is known.
This is the decision §02 flagged as app-wide. It is settled here for the chart and holds for all eight assembly types: a title-hidden assembly reserves nothing. For a table that means the strip covers the first row's right edge, for a selection list the first item's — both recoverable, both on hover, neither a layout change.

reuse existing directive
The title stays one line and ends in an ellipsis. It must not wrap: the lane's height is what the plot box is anchored to, so a wrapping title would make lane height depend on string length — the same dashboard would reflow differently per chart, and the strip, absolutely positioned at the lane's top inset, would no longer sit centred against the title.
Put tooltipIf on the title element. The directive ships at widget/tooltip/tooltip-if.directive.ts and does exactly this job: it compares scrollWidth > clientWidth each change-detection pass and sets or removes a native title accordingly, so the tooltip appears only when the text is actually cut. Reads and writes go through DomService, so it does not thrash layout. No new component, no positioning code.
Native title is hover-only: no tooltip on touch, none on keyboard focus, and screen-reader support is inconsistent. Accepted here — it is what the mini-toolbar buttons already use (a native title bound to action.label() plus a visually-hidden span), so the card stays consistent with the toolbar beside it. This matters most at the bottom of §06's ladder, where the title truncates hardest.

04

Spacing — the card interior

The card is five nested boxes and only one of them is elastic. Axis label bands, axis title bands and the legend column size to their own content; the title lane takes the greater of its type box and the toolbar strip — the target model, though the shipped strip overlays the lane rather than sizing it, reconciled below; the plot is whatever is left. Stating that is most of the spec — the numbers below are the default-density instance of it, not the rule. Each edge has exactly one owner, so no two rules ever apply to the same gap — and where a nested region does set its own inset, it replaces the card's rather than adding to it.

Hidden means zero — including the gap and the rule
rule
Authors hide the title, either axis title, either axis labels and the legend independently. A hidden element contributes no height, no width, and no gap — the plot claims the space. Every gap in the table belongs to the element on the content side of the arrow, so it disappears with it; there is no such thing as a reserved band for something not drawn.
The lane rule belongs to the title, not to the card. Hide the title and the 1px divider goes with it — there is no band left to underline, and a rule under nothing reads as an empty one. This is the one piece of chrome that could plausibly be treated as a card fixture, so it is worth naming: it is not.
And the lane goes with it. §03 covers why — nothing is reserved, so the plot claims the whole band and the strip overlays its top-right corner. The tick label's clearance comes from the plot's own internal padding, not from a lane, so hiding the title costs the plot nothing and reflows no existing dashboard.
Axis titles and label bands vanish entirely, along with their 4px and 8px gaps, and the chain closes up: with the y labels hidden but the axis title kept, the title sits 8px from the plot — it inherits the gap of whatever it now abuts, rather than keeping its own 4px. Where text height comes from
rule
Every intrinsic band in the table is a line box, not a pixel value: its height is the font size times the line-height, and authors change both per chart. So no band can be given a fixed height — the spec fixes the gaps and lets the type determine the rest.
Line-height 1.2 for all chart text (--inet-chart-line-height) — title, axis titles, tick labels and legend labels. Tight enough that a two-line title does not look loose, loose enough that descenders never clip. This is the one type value this spec adds; sizes stay with the author.
Title lane height = title line box + 12px above + 8px below — or the strip's height plus the same gaps, whichever is greater. At the default 13px title the line box is ~16px, so the 30px strip wins and drives the lane; the title only takes over above roughly 24px type. When the strip governs, the title centres vertically in that band, so at default type the text top sits ~20px below the card border while its box still starts at 12px. Only the box edge is a spacing rule; the text position falls out of the centring.

Not what shipped, and worth reconciling. This rule assumes the strip participates in the lane's height. It does not: .mini-toolbar is position: absolute at a computed top/left/width, so it overlays whatever lane the title produces rather than growing it. The good news is that anchoring therefore cannot shrink the plot on any existing chart — no reflow, gate on or off. The cost is the inverse risk: where the title's own lane is shorter than the strip, the strip overhangs it and covers the top of the plot instead of the lane expanding. At the default 13px title that is a ~14px overhang for the 30px strip, and 44px on touch. Either implement the "whichever is greater" rule in the lane math, or restate this as an overlay and specify the overhang — but the spec and the code should not disagree about which one it is.
Axis label bands = the longest label's line box, plus its 8px gap to the plot. Rotated x labels use the rotated bounding box, which is why a long category axis can consume a third of the card and still be correct.
Consequence worth stating in review: because the strip sets the lane height at normal type sizes, changing the touch target from 30px to 44px makes every card's lane taller and every plot shorter. That is the real cost of the touch density, and it is why 44px applies on touch only.

Floating is a drag result, not a fifth dock
verified in repo
All five come from one interaction. chart-legend-container.component.ts tracks the drag and classifies the drop by whether the legend has been pulled past a chart edge — newTop < chartRect.top, newLeft < chartRect.left, or the trailing edge beyond the chart's right or bottom. Cross one and the legend docks to that side, and a preview outline one tenth of the chart's width or height is drawn to show where it will pin. Drop it anywhere inside the chart and the area is CENTER: VSChartMoveLegendService then sets IN_PLACE and stores the raw Point2D on the LegendDescriptor.
So the floating legend has no anchor and no gap. Its position is whatever point the author dropped it at, held as an offset from the chart's top-left — it can overlap the plot, sit in the margin, or straddle both. This spec must not give it a spacing rule; the surface treatment is the only thing it can specify.
Resize follows the same split: a docked legend resizes only on its plot-facing edge (getResizeEdges() — RIGHT gets LEFT, and so on), and is clamped to half the chart. Floating resizes from right and bottom, and falls through to the default clamp of 0 to the full chart width. Both drags need a target big enough to grab — see §03's control sizing.

Degradation order

Authors resize freely, so the card must have a documented order in which things go. Each step fires only when the step above cannot buy enough room. Steps 1–5 are about width and content; the toolbar has its own ladder, driven by height, specified below them.

When the toolbar itself degrades — height first, kebab last
rule
The existing machinery only knows width. allowedActionsNum() is floor(objectFormat.width / actionWidth), where MiniToolbarService.getActionsWidth derives actionWidth from the root font size — 18px glyph + 4px icon padding + 1rem button padding + 2px border, so 40px at a 16px root. Height is never consulted, so a 400×24 chart passes the width test and still cannot host a 30px strip.

The title-hidden card has one size, not a ladder. The table above is the in-lane strip. When the title is hidden the strip is overlaid, and §03 fixes it at the 24px small step at every height — it is small because it sits over the plot, not because the card is short, so it never occupies the comfortable row. Read the table for it this way: the top two rows collapse into one — at any height above 56px the overlaid strip is three 24px actions plus the kebab — while the bottom two rows govern it unchanged: 32–56px is kebab only, and below 32px there is no chrome. A 40px card cannot host three actions whether they sit in a lane or over the plot. So a 200px title-hidden card is 24px and a 200px card with a title is 30px — same height, different strip, because they are in different places. The 44px touch floor is not one of these rows; it overrides all of them, as set out below.
Two rules, and the second is the point. Width caps the action count at Math.min(3, allowedActionsNum()) — a ceiling on machinery that already exists, not new machinery. Height decides the row above. And in both directions the kebab is the last thing to go: actions drop one at a time, the kebab survives them all, and only the final row removes it. That ordering is what keeps §02's resting affordance meaningful at every size a card can reach.
Touch has no ladder — it has one row. The action buttons are inside @if (!mobileDevice) and this spec leaves them there, so on touch the kebab is the whole strip regardless of height (§02). It takes the 44px hit-target floor rather than any height band: at 52px and above (44 + 4 + 4) the kebab renders, below 52px there is no chrome. A 70px card is three 24px actions plus a kebab on a pointer device and a single 44px kebab on touch. Never satisfy a height band by shrinking a touch target below 44px — drop the control instead.
Every rung shows the same list — §02's rule, restated because the ladder depends on it. The kebab is not an overflow control that empties as the strip grows: per §02, overflowed toolbar actions are prepended to the menu groups for both entry points, so the kebab and right-click always present one identical, complete list. That is what makes the lower rungs safe. At kebab-only nothing has been lost, only the shortcuts; at no-chrome the same list is one right-click away. It also means the kebab is never empty on an assembly with three or fewer actions — which matters less on a chart than on the 150px selection lists this pattern rolls out to, where an overflow-only kebab would vanish exactly where the resting glyph is the only affordance. On touch the action buttons never render at all, so this list is the interface.
Fix the menu gap before relying on this ladder. show-data and open-max-mode / close-max-mode are toolbar-only today — createMenuActions does not carry them, so right-click cannot reach them at all. That is a standing bug, independent of this spec. §02's concatenation happens to paper over it: once suppressed, those actions overflow, and overflow is prepended to both entry points, so they stay reachable. Do not lean on that. It makes the one action whose purpose is rescuing a chart too small to read reachable only as a side effect of overflow arithmetic — and it breaks the moment anything stops building the toolbar array for a suppressed assembly. Add them to createMenuActions so the guarantee holds structurally. Not a blocker for §02, which ships on its own.
Where the numbers come from — one is derived, two are judgement. Only 32px follows from anything: a 24px control needs 4px of clearance above and below, so below 32px no control fits and the question answers itself. 56px (32 + 24) and 96px (3 × 32) are expressed as steps off that floor so they at least move with the control tokens, but nothing computes them — they are the heights at which a strip stops feeling like it owns the card, and they are the part of this rule most likely to be wrong. Validate against real dashboards before implementing: a 56px card is common in a KPI row.

Authors can set the font and the outlines follow, but no stylesheet can restyle chart type: changing --inet-font-family reskins the shell and leaves the chart untouched. Type reaches the chart only through its own format model or the server property.
The default family is SreeEnv.getProperty("default.font.family", "Roboto") — StyleFont's "Default" is a sentinel resolved to that at construction. Roboto is also in the shell stack and ships as roboto-fontface, so the two renderers agree on family by default.
This spec treats outlined text as a given. Every rule in §04 and §06 is stated in geometry, not type styling, so nothing here depends on the conversion. Converting to <text> is one boolean at SVGUtil.java:63 and a large amount of everything else — written up in Outlined chart text - ticket.md.
One prerequisite is worth naming here because it is a token decision, not a rendering one: the server starts from GDefaults 9 / 10 / 11pt while the browser base is 13px. Name the chart's type scale at its current rendered sizes before any conversion, or the switch silently re-lays out every chart. Also: if chart labels render in a different face than the shell, check the configured family is installed on the render host — the JDK falls back silently to 'Dialog'.
Subtitle, deferred
TitleInfo exposes one string and a visibility flag. A real subtitle is a model change with serialisation, property sheet, and migration attached — proposed separately. Still true on epic-74519: vs-chart-model.ts carries a bare titleVisible: boolean, the same shape as every other assembly model.
10

Chrome on a background the author owns

The card background is author-set, and the controls drawn on it are not. Three rules follow from that, and none of them belong to the toolbar specifically — §02 is their first consumer, the eight-assembly rollout is the next, and any future glyph drawn on a card inherits them. Two are decided; the third is an open question this spec has to answer before dark mode ships, not after.

Scope — everything here is read-time, so the seed mark does not reach it
Two mechanisms decide whether a modern value applies, and confusing them is the likeliest misreading across this spec and the visualization widget spec. The gate — .viz-modern on document.body, read through GuiTool.isVizModern() — turns read-time styling on and off for every dashboard at once. The seed mark is a tri-state provenance field on VSAssemblyInfo recording which branch ran when an assembly was created, and it exists so values written into the saved asset stay reversible.
All three rules in §10 are read-time CSS under the gate. Nothing here is written into a saved asset, so nothing here is marked, and none of it waits on the mark to ship. Turn the gate off and it all reverts everywhere at once — on claimed and unclaimed dashboards alike — because there is no per-assembly condition to consult.
What the mark does govern on this card is §01. The frame, the radius and the card background are seeded by VSObjectChromeDefaults into the asset at creation. The chart is one of the eight seeded types, so its card chrome is marked and gated on exactly the same terms as every other widget — that half is ordered mark before shell before chart; §10 is not.
The mixed object to expect. An unclaimed card in a gate-on product keeps its legacy square corners and no frame while everything in §10 modernizes anyway — a modern glyph on a legacy card. That is a consequence of the split, not a defect in either rule, and it is what the sibling spec's per-dashboard Modernize action exists to resolve.
10.2 is the one rule immune to all of it. Deriving tone from the rendered background means it does not care which mechanism produced that colour — legacy seed, modern seed, author override or dark resolver. It reads what is actually there, so it stays correct through every combination of mark and gate without a branch.
10.1 · Resting visibility is a pointer-capability question
decided
Hover-revealed chrome is the cheapest way to keep a dashboard quiet, and it is unavailable on touch, where hover does not exist. Rather than choose one, scope the resting draw to the devices that need it. One capability query carries the whole rule — no user-agent test, no JavaScript, no device list to maintain.
.chart-card .kebab { opacity: 1; } /* touch: drawn at rest */ @media (hover: hover) and (pointer: fine) { /* mouse, trackpad */ .chart-card .kebab { opacity: 0; transition: opacity .12s; } .chart-card:hover .kebab, .chart-card:focus-within .kebab, .chart-card .kebab:focus-visible { opacity: 1; } }
The kebab hides by opacity; the action groups leave layout. These are two different rules and an earlier draft of this spec wrongly stated one. The kebab must use opacity — never display: none or visibility: hidden — because a transparent button keeps its tab order and its accessible name, which is what lets the keyboard route survive the hiding. The three action groups use display, and that is deliberate: the pill is width: fit-content right-aligned by an auto margin, so transparent-but-in-layout buttons would leave a wide empty pill sitting at rest instead of one wrapped tight around the kebab. Leaving layout also settles hit-testing, since .mini-toolbar-button-group sets pointer-events: all unconditionally and a merely transparent button would still be clickable. Nothing reflows either way — see the overlay note below.
Nothing here can reflow the card. .mini-toolbar is position: absolute in every state, anchored or floating — it is placed at a computed top/left/width and is not a layout child of the card. The host spans the lane and the pill shrink-wraps inside it, so the reveal grows leftward into space the host already owns. Revealing, hiding and the touch target all move nothing.
One capability idiom, not two. mini-toolbar.component.scss already carries a @media (pointer: coarse) block for the 44px touch target. That is a different test from this one — coarse asks how precise the pointer is, hover asks whether revealing on hover is possible at all, and the second is the question here. Keep both queries but comment why they differ, or a later reader will collapse them into one and change behaviour on hybrids.
Hybrid laptops follow the pointer rule. A touchscreen laptop reports hover: hover for its primary pointer, so it reveals on hover; a tap still opens the menu, it is simply not pre-revealed. :hover can stick after a tap there, which is harmless. If it ever isn't, a pointerdown listener recording pointerType === 'touch' on a body attribute short-circuits the query.
Where the control is the only chrome, this rule empties the card. An assembly whose strip is a kebab and nothing else — the selection family, and any card in §06's 32–56px rung — shows no chrome at rest on a pointer device. That is the quietest possible dashboard and it may well be right, but it is a different proposition from hiding two of four controls, and it should be agreed deliberately per family rather than inherited from this rule. Chart and the table family, which keep three actions plus the kebab, are unaffected either way.
10.2 · Glyph tone is derived, not fixed
decided
No fixed treatment stays legible across an author-set background. A white rounded box with a border reads correctly on a saturated card and dissolves on a light grey one, where box, border and card are all near-white. Drop the box. Draw the glyph alone, in one of two tones, selected from the relative luminance of whatever it sits on.
The threshold
Standard WCAG relative luminance of the resolved background colour, against L > 0.45 → light tone, otherwise dark tone. Below the midpoint deliberately: mid-tone saturated colours read darker than their computed luminance suggests, and 0.5 puts several common brand teals and greens on the wrong side. Computed once per background change — not per frame — and written to the card as data-tone="light|dark" so every style stays in CSS.
#E8563F · L 0.24 → dark tone
#2FC4B2 · L 0.43 → dark tone. The borderline case — check this one first if the threshold is questioned.
#C8CCC9 · L 0.60 → light tone. The case a white box fails on.
#FFFFFF · L 1.00 → light tone

The hover background is a translucent tint of the glyph colour rather than a fixed grey, so it adapts with the tone and never needs a border to separate it from the card. These two resting alphas are the resting opacity — do not apply a further multiplier from §02 on top of them.
One implementation precondition. The glyph is an <img> in mini-toolbar.component.html today, and color cannot tint an image. Either switch to an inline SVG using currentColor — preferred, since it makes the two tones one property — or drive them with a filter: invert() pair. The swatches above use the filter route, which is why the dark-tone dots are the same asset inverted.
Card luminance is not enough when the glyph overlays the plot. In the title-hidden state (§03) the glyph sits over gridlines, bars and possibly a light-on-dark series, so the background varies underneath a single control. There, and only there, add a scrim: a 28px rounded patch in the tone colour at ~8% alpha with backdrop-filter: blur(2px). It reads as a softening of the plot rather than a button. Giving every widget the thin title band the coloured ones already have removes the need for it entirely, which is the better structural answer where it is available.
Three alternatives ruled out. mix-blend-mode: difference needs no threshold and no script, but it inverts hue rather than lightness — a coral card yields cyan-green dots — and it goes invisible against mid-grey, the most common dashboard background. contrast-color() is exactly this rule as one CSS function and should replace the script the moment support allows; today it ships in Safari only. light-dark() does not apply — it switches on color-scheme, not on an arbitrary author colour.
10.3 · Dark mode — the server has the card's values, this spec has not reconciled with them
deferred — see Chart card dark values - ticket.md
Dark mode is further along than an open question. It is an org property — viewsheet.darkMode, gated behind viewsheet.modernVisualization — with a .viz-dark body scope in _viz-tokens.scss, and the card's own dark values already exist server-side: VSObjectChromeDefaults defines card background #252428, object border #49454F, page canvas #1C1B1F and text #E6E0E9, plus an applyDarkForeground resolver that substitutes light text onto a clone at both model build and export. So this is a reconciliation, not a blank page: this spec states its greys as light-mode literals and has never been checked against those four values. What is genuinely undecided is the chart interior, not the card.
10.2 narrows the question rather than answering it. A luminance-derived tone is dark-mode-correct by construction — the shipped dark card background #252428 computes to L ≈ 0.02, well under the 0.45 threshold, so the glyph flips to the light tone with no dark-mode rule at all. The rule reads the actual colour rather than a mode, which is why it needs no branch. That covers the toolbar glyph and nothing else. Everything specified as a literal still needs a dark value: the card frame and its border colour, the title and axis text greys, the gridlines, the plot background, the legend rule, and the tooltip and selection surfaces §07 covers.
The chart is the hard half, but not for want of a mechanism. Card chrome is DOM and inverts through tokens, and the server already holds its four dark values. The plot is server-rendered SVG with outlined text (§09), so its greys come from GDefaults and no stylesheet reaches them. What the plot is not is untouched by the gate: ChartVSAssemblyInfo sets plotDesc.setBarCornerRadius(0.3) and PlotDescriptor.getBarCornerRadius() reverts it when the gate is off, so a gated server-side path into the plot already exists and already has a reversibility story. Dark chart values would have somewhere to go. What is missing is the palette decision, not the plumbing.
Deferring is a legitimate answer. Scoping dark out of the chart pilot is defensible; leaving it unstated is not, because the pilot then ships a card that silently cannot follow the product. Whichever way it goes, it should be written here.
If it is in scope, it is a section, not a column. Dark is not a second value beside each grey — it changes which surfaces carry elevation and which carry a border, and this spec leans on borders throughout (§01, §05). That is design work, not a token sweep.
Raised by the cross-spec audit in the sibling Visualization Widget Spec, where dark is already shipped for calendar chrome. Recorded here because it is a chart-card absence rather than a viz-side open item — §09 lists it in the open queue.
